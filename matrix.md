# Client SDK debug logging: failure-mode matrix

Research date: 2026-10-29. Proposed behavior: optional `debugMode: boolean`, default `false`.

This matrix specifies what customers should be able to diagnose from local debug output. It covers the eight integrations listed in the [client SDK documentation][DOC_CLIENT]: JavaScript, React, Angular, Android, iOS, React Native, Dart/Flutter and Unity. React and Angular share the Datadog browser provider; React Native adds JavaScript/native boundaries. Dart and Unity implement their own flag transports.

The research used pinned snapshots of seven Datadog repositories and followed flag setup, context handling, fetching, parsing, storage, evaluation, tracking and shutdown into the relevant shared transports and native dependencies. This is an end-to-end source audit of the feature-flag paths, not a claim that every unrelated RUM/tracing file in those repositories was read. Relevant tests were inspected, not executed. The source references below are pinned to the audited revisions. These are source-head observations, not release-status claims.

**The table below is an applicability and implementation-ownership matrix, not a scorecard of debug logging already implemented.** All applicable checklist items should be exercised on each SDK. Platform-specific cells describe how the scenario arises; they do not excuse missing diagnostics.

Conditional features must log their actual configuration: `disabled`, `unsupported`, `application_managed` or the enabled implementation. They should not be silently treated as failures. Initialization, a cache miss, an intentional cancellation and an intentionally suppressed exposure can all be normal debug events.

## Shared scenario checklist

Each row describes a scenario to reproduce and the required observable outcome. Log the successful path and recovery as well as errors. Otherwise customers cannot tell whether an operation ran at all. IDs match the matrix columns.

## Proposed debugMode contract

Expose the same optional Boolean concept in each SDK's provider initialization/configuration API, using platform naming conventions. Set it before the first validation, client lookup, cache read or network operation. For JavaScript, that fits the provider's existing options:

```typescript
const provider = new DatadogProvider({
  applicationId,
  clientToken,
  site,
  env,
  debugMode: true, // proposed option
})
```

Keep OpenFeature's lifecycle signature compatible; its framework calls `initialize(context)`. A second Boolean argument there would not automatically be supplied by OpenFeature, and browser constructor validation already happens earlier. Android/iOS builders or initializers, Dart configuration and Unity's Enable configuration need the equivalent option. Propagate it through wrappers and native layers before work starts. [Browser constructor/lifecycle][B1], [RN client construction][R1], [Unity enable][U1].

Debug mode should be sufficient by itself to make these flag diagnostics visible, without requiring a second global verbosity setting. Keep it scoped to the provider/client where possible, and label shared transport diagnostics with the owning client and channel. Do not turn on unrelated RUM/tracing debug logs globally.

Use the platform's local developer output: browser/React Native console, Android Logcat, iOS device/Xcode console, Dart's platform-compatible console mechanism, Unity Console/player log. These are the client equivalents of server standard output; they are not all literal process stdout. Prefer an ordinarily visible console level or document the exact filter. The debug logger itself should not create remote telemetry events; preserve existing internal-log forwarding exclusions such as Unity's.

Honor the agreed full-value policy: include complete raw flag values, defaults, evaluation contexts, normalized contexts, configuration payloads, assignment metadata and event payloads. Do not redact or truncate targeting inputs. Transport credentials remain separate: record their presence/source and non-secret routing information rather than API keys, client-token values or authorization headers, including credentials in URL query strings. If a platform limits line length, split complete payloads into numbered, correlated chunks. Snapshot values at event time so a developer console cannot later display a mutated object as the earlier context.

Debug output must not change assignments, context, readiness, callback ordering or tracking policy. Evaluate neither targeting getters nor serialization code a second time just to log. Handle unsupported/circular values without throwing, and do not pay full serialization costs when debug mode is off.

## Common log fields

| Field group | Required information                                                                                                                                                         |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Identity    | `event`, timestamp, SDK/provider and native versions, platform, provider instance ID, client/domain, runtime/isolate where relevant                                          |
| Correlation | Operation/request ID, parent operation, context revision, local configuration revision, evaluation ID and event/batch ID as applicable                                       |
| State       | Previous/new state, requested context, installed assignment context, config source, install time and age; upstream config ID/createdAt only when actually available          |
| Outcome     | `outcome`, stable reason/error code, raw exception details, action taken, retry/backoff or terminal disposition, monotonic duration                                          |
| Evaluation  | Raw flag key, requested type, runtime default, raw effective context, returned value, value origin, variant, reason, allocation/rule/serial metadata and complete assignment |
| Channel     | `configuration`, `exposure`, `evaluation`, `rum` or `debug`; endpoint and transport, policy/eligibility, queue state and delivery stage                                      |

Use a locally generated revision if the service does not supply a configuration ID. Do not fabricate server identifiers, server rule traces or precise network causes. Explicit `unknown` or `not_available` is preferable to misleading confidence.

## Acceptance criteria

Replay every applicable scenario against each SDK with `debugMode=true`. For a single flag, the output must answer: Which client is running? Which identity and attributes were used? Which configuration supplied the assignment? Why was this value or runtime default returned? Was an exposure eligible, deduplicated, queued, accepted by intake, retried or dropped? What should cause the next refresh or recovery?

Start with these cross-platform sequences: clean initialization and successful evaluation; evaluate before ready; invalid setup; missing key/invalid attributes; login and logout; wrong flag/type; fetch 401/403/429/500 and transport failure; malformed and partially valid responses; cold offline start; same-context versus different-context cache fallback; deadline followed by late success; overlapping context changes; reset/close during fetch; disabled/deduplicated exposure; terminal and retryable event-upload errors; background/exit with pending work. Then apply the SDK-specific bridge, IndexedDB, consent, framework, isolate and main-thread scenarios above.

Repeat representative success/failure paths with debug off and with an unavailable/throwing sink. Verify results and lifecycle behavior remain unchanged. Captured debug traces should be the evidence for future implementation-matrix checkmarks; source inspection alone is not a runtime pass.
